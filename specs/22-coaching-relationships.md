# Task 22 — Coach and coachee relationships
Assignee: nick3105

## Why

A person can invite a friend or family member to coach them. After accepting, the coach can
create their workout plans and review their completed training in a clearly identified workspace.
This introduces an explicit exception to the BRD's private-journal baseline. Access starts only
after the coachee requests it and the named coach accepts.

## What

Extends ACC-04, NAV-02, PLN-01, PLN-10 and REV-01 to REV-03. Proposed new requirement group
`COA` covers the relationship and delegated access. Add these requirements to the BRD with the
implementation PR.

- In signed-in Settings, show Assign coach, a username field and a short permission explanation.
  Before sending, explain that an accepted coach can see saved workout templates, completed
  sessions, exercise progress and workout/exercise notes, and create plans for this coachee.
- The coachee enters an existing username. Resolve it case-insensitively using the same
  normalization as sign-in. Reject their own username and give a readable error for an account
  that cannot be assigned. Sending records a pending request and grants no journal access.
- The recipient sees the coachee's username and the requested permissions in Settings, with
  Accept and Decline. Only that recipient can accept. A coachee can cancel a pending request.
- An accepted coach gains a Coachees item in the desktop sidebar. At 375 px, use a reachable
  More/Settings menu or equivalent secondary navigation instead of squeezing additional items
  into the existing five-item bottom bar. Pending requests remain reachable before acceptance.
- Coachees opens a list of accepted coachees. Selecting one opens a workspace headed
  "Coaching <username>" on every screen. Its builder creates templates owned by that coachee,
  visible in their normal Start workout list. Show who created the plan.
- The coach can inspect that coachee's completed sessions, exercise progress and shared notes.
  Own-journal routes continue to use the signed-in user's journal. Keep the selected coachee
  and unsaved drafts separate from the coach's own active workout.
- Both people can end an accepted relationship in Settings after confirming. Recheck the
  relationship on every delegated request. Revocation takes effect for the next request,
  including a save from a coach page that was open before revocation. Keep plans already
  owned by the coachee and preserve historical creator attribution.
- New relationship rows reference immutable user IDs. Record requester, recipient, state and
  UTC creation/decision times. Add a schema-version migration through storage.initialize that
  preserves all existing accounts, templates and sessions. Transition pending/accepted states
  atomically, with uniqueness constraints and idempotent retries. A stale accept after cancel
  or revoke must fail without restoring access.
- Proposed API shape is own Settings relationship endpoints plus a dedicated
  `/api/coachees/<user_id>/...` namespace. Every delegated route derives the actor from the
  signed-in session, verifies an accepted relationship, then queries the explicit owner.
  Check permission and perform a delegated write in the same database transaction, so a revoke
  cannot slip between authorization and commit. Never accept a body user_id as authorization.
  SQL lives in storage.py, permission rules in
  models.py and request handling in app.py. Apply authentication and CSRF to mutations.
- Relationship responses contain usernames, IDs needed by the view and state only. Coach
  responses exclude body-weight records, weight goals, password hashes, settings and account
  recovery/security data. A pending or unrelated user receives no journal records.

Proposed defaults for review before implementation

- One accepted coach per coachee, any number of coachees per coach. Allow one outgoing pending
  request. Replacing a coach ends the previous relationship before a new request can be sent.
- A coach can create and edit plans they created for that coachee. Existing coachee-created
  plans and all completed sessions are read-only for the coach. Deletion stays with the owner.
- Accepted access includes existing training history and future training until revoked. Make
  that scope explicit before the coachee sends the request. A narrower historical date range
  would need an additional product decision.
- Permit both people to coach others, but reject self-coaching. No age-based privileges are
  inferred from a family relationship.

## Out of scope

Paid coaching, messages, exercise prescriptions generated by the app, body-weight sharing,
coach access to passwords or account settings, and coach corrections of performed results.

## Done when

- At 375 x 667, Alice enters Bob in Settings, sees the sharing explanation and sends a request.
  Bob sees Alice's username and can accept with a target at least 44 x 44 px. Before acceptance,
  Bob cannot read Alice's templates, sessions, progress or notes through any API route.
- Bob accepts, opens Coachees and creates "Alice upper" with Bench press 3 x 8 at 40 kg. Alice
  signs in on another device and can start that plan. Bob's own Start workout list is unchanged.
- Bob reviews Alice's saved workout with its notes. A third account cannot read or mutate
  either journal by replacing user, template, session, relationship or exercise IDs in requests.
- Alice revokes while Bob has an unsaved plan open. Bob's next read/save fails, the page removes
  cached coachee data, and Alice keeps earlier plans and history. Re-accepting an old request
  fails. The same checks apply when Bob ends the relationship.
- Decline, cancel, duplicate Send/Accept and simultaneous accept/revoke have deterministic
  results and never create two accepted coaches. Self-assignment is rejected in the API.
- The schema-upgrade test starts with a populated previous-version database and preserves it.
  Tests prove that delegated responses contain no body weights, goals or security fields.
- No horizontal scrolling at 375 px. Keyboard users can assign, accept, navigate and revoke.
  Switching workspaces warns before losing an unsaved draft. Include a real-phone screenshot
  before merging, and run all repository checks.
